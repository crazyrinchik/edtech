# Совёнок

Платформа дополнительного образования для 1–4 класса: математика и русский язык
короткими занятиями. Три интерфейса в одном приложении — ребёнок, родитель, администратор.

Прод: https://sovenok.space

## Что умеет

**Без регистрации.** Нулевой урок из семи заданий (`/demo`) и пять тренажёров: устный
счёт (`/schet`), таблица умножения (`/tablica-umnozheniya`), правописание
(`/pravopisanie`), скорочтение (`/chtenie`, простой уровень) и таблица Шульте
(`/shulte`). Упражнения открыты целиком, но в базовой настройке: разрядность,
таймер, уровень таблицы и набор правил меняются по подписке, и по ней же заход
где-то остаётся. Прогресс не сохраняется, и на экране результата об этом сказано
прямо. См. «Где проходит граница подписки».

Два тренажёра устроены вокруг подсказки, а не вокруг проверки: в правописании к каждому
упражнению раскрывается правило, в таблице умножения — сама таблица Пифагора с
подсвеченной клеткой. После ошибки подсказка разворачивается сама. Подсмотреть тут
полезнее, чем угадать: угаданное не запоминается.

Во всех пяти на время упражнения включается ночь: тёмный фон со звёздами, счётчик
верных подряд, разгон с третьего ответа и вспышка с залпом на каждом пятом. См.
«Аркадный слой тренажёров».

**Ребёнок.** Карта тем с последовательным открытием, задания трёх типов (выбор варианта,
ввод ответа, сопоставление), мгновенная проверка, разбор ошибки словами вместо «неверно»,
проверочная работа с порогом 70% для зачёта темы, звёзды за пройденные темы,
мягкое напоминание об отдыхе через настраиваемый интервал. Любое задание читается вслух
по кнопке-ушку (синтез речи браузера) — читать для начала занятия не обязательно.
Если детей несколько, занятие начинается с выбора профиля по аватару и имени.

**Взрослый.** Один кабинет на родителя и репетитора (`/kabinet`), без анимаций:
сколько дней подряд ребёнок занимался (тема и тренажёр в этой серии равны), пять
тренажёров с рекордами серий и кнопкой «задать» у каждого, домашка, занятия по
темам с историей и долей верных, зоны риска (ниже 70%), лимит времени и звук,
управление подпиской, несколько детей в аккаунте, напоминания в Telegram или MAX.
Вход в приложение единый, а семейный кабинет открывается кодом из четырёх цифр.
См. «Кабинет взрослого».

**Администратор.** CRUD тем и заданий: весь каталог с вариантами под программы, задания
правятся на месте (текст, тип, варианты, ответ, разбор), тему можно вернуть к набору из
генератора;
DAU и WAU, конверсии (регистрация → первое занятие, доля открывших родительский кабинет,
доля оплативших), проблемные и популярные темы, блокировка пользователей и выдача
подписки вручную.

## Стек

- TanStack Start (React 19, SSR) + TanStack Router
- workerd (через miniflare) как рантайм — на своём сервере, не в Cloudflare
- PostgreSQL как база, доступ через внутренний шлюз с интерфейсом D1
- Caddy: статика, TLS, обратный прокси на SSR-worker
- Vite, TypeScript, Tailwind
- Zod для валидации входных данных серверных функций

Всё это крутится на одной машине в Яндекс.Облаке. В Cloudflare приложение
не выкладывается: персональные данные детей по ч. 5 ст. 18 152-ФЗ должны
храниться в базе на территории России. Конфигов для деплоя в Cloudflare
(`wrangler.jsonc`, `app.manifest.json`) в репозитории нет намеренно —
не возвращайте их. Юридическая обвязка живёт в `docs/legal/`.

## Задания по программам

Набор тем в классе один для всех учебников (ФОП НОО), а уровень заданий внутри темы —
нет: второклассник по Петерсон складывает трёхзначные в столбик и знает всю таблицу
умножения, по Школе России в это время умножают на 2 и 3, а у Эльконина — Давыдова
число вообще появляется из измерения меркой. Поэтому у темы может быть свой набор
генераторов под программу (`practice.programs.ts`); там, где программа идёт базовым
темпом, набор общий, и экран «Повторение школьной программы» говорит об этом прямо.
Школа России в реестре отсутствует намеренно — это и есть базовый темп.

- Тема под программу живёт в базе отдельной строкой `код@программа` с именем вида
  «Табличное умножение · Петерсон», задания у неё свои (`код@программа#номер`). На карту
  ученика такие строки не попадают: ребёнок получает их домашкой от взрослого, который
  выбрал программу на экране «Повторение школьной программы».
- Условия написаны свои, из программы взят только уровень: числа, действия, термины.
  Тексты задач из учебников не переписываются — это авторские произведения.
- В базу тема попадает при первом открытии и дальше генератором не трогается: правки
  администратора переживают выкладки. Если генераторы поправили, а тема уже лежит в
  базе со старым набором, в админке есть «Вернуть задания из генератора» — с потерей
  ручных правок, о чём кнопка спрашивает.
- `bun run scripts/check-practice.ts` прогоняет все наборы: тридцать непохожих карточек
  на тему, ответ среди вариантов, ничего не «NaN». Ошибка генератора — это неверный
  ответ у ребёнка, поэтому проверка должна быть зелёной до коммита.

## Аркадный слой тренажёров

Тренажёр для первоклассника конкурирует не с учебником, а с играми, и спокойные
примеры на светлой бумаге он закрывает раньше, чем досчитает до десятого. Поэтому
на время упражнения вокруг него включается ночь и считается серия.

Что в ней есть: счётчик верных подряд (появляется со второго), разгон неба с
третьего ответа, вспышка с тряской и залпом на каждом пятом, нота, поднимающаяся
по пентатонике с каждым ответом серии, и «лучшая серия» на экране итога. Ошибка
серию гасит, но не наказывает: ни красного креста, ни звука провала — правила
«вместо оценки разбор» аркада не отменяет.

Живёт всё в двух файлах: `lib/arcade.ts` (небо и искры в canvas, звук в Web Audio)
и `components/arcade.tsx` (хук состояния и разметка). Подключается одинаково во
всех пяти тренажёрах тремя строками:

```tsx
const arcade = useArcade();                   // состояние серии
<ArcadeStage arcade={arcade}>…</ArcadeStage>  // ночь, искры, вспышка
arcade.hit(ok, event.currentTarget);          // на каждом ответе
```

Три решения, которые из кода не видны:

- **Ночь только на упражнении.** Экран настройки остаётся на бумаге: там читают,
  что вообще делать, а в правописании и чтении — ещё и длинные списки. Витрина,
  кабинет родителя и карта тем ночи не видят вовсе.
- **Ночь — это переопределённые токены, а не новые правила.** `.sov-arcade`
  переназначает `--sov-paper`, `--sov-ink` и остальные, поэтому карточки, пилюли и
  разбор ответа перекрашиваются сами. Точечных правил ровно столько, сколько
  элементов залито белым напрямую: карточка, кнопка-ушко, поле ввода, поле слова
  в скорочтении, клетки Шульте.
- **Без Lottie.** Плеер стоит около шестидесяти килобайт на каждом экране плюс вес
  анимации, а всё, что он давал бы здесь — искры, вспышка, залп, — рисуется
  частицами в паре килобайт. Тянуть его имело бы смысл ради сложной сцены с
  персонажем; такой сцены в тренажёре нет.

Серия считается по-разному там, где механика разная. В счёте, таблице и
правописании — по ответам; кончившееся время рвёт серию так же, как неверный
ответ, иначе выгоднее молчать. В таблице Шульте — по числам, найденным подряд без
промаха. В скорочтении ответов во время чтения нет, а оба вопроса ребёнок
отмечает до проверки, поэтому серия разворачивается на экране итога: ответы
загораются по одному, и только потом даётся залп.

Звук по умолчанию выключен, переключатель стоит рядом со счётчиком, выбор
запоминается в браузере (`sov.arcade.sound`) и переезжает из тренажёра в
тренажёр. Настройка звука в кабинете родителя к этому отношения не имеет: она про
занятия и приезжает только вошедшему, а тренажёры открыты и без аккаунта.

`prefers-reduced-motion` выключает движение целиком: звёзды стоят, искр нет,
вспышка и тряска не проигрываются. Счётчик серии при этом остаётся.

**Серия переживает заход.** Лучшая серия каждого захода ложится в `drill_streaks`
(`drill_id`, `best`) — отдельной таблицей, а не колонкой в `drills`: миграции
идемпотентны и гоняются на каждом старте, а `ALTER TABLE ADD COLUMN IF NOT EXISTS`
в SQLite нет. Строка появляется только у серий от двух; рекорда ребёнка в базе нет
и не будет — это `MAX` по заходам того же тренажёра, и считается он до вставки,
иначе свежая серия попадала бы в собственный рекорд. Когда серия побила прошлые,
экран итога говорит «новый рекорд», а кабинет родителя показывает рекорд рядом с
долей верных. Без аккаунта рекорда не бывает: сравнивать не с чем.

Серию присылает клиент — кроме скорочтения. Там во время чтения ответов нет, оба
вопроса ребёнок отмечает до проверки, и какие из них верные, экран узнаёт из того
же ответа сервера, которым заход и сохраняется, — поэтому серию считает
`readingResult` по тем же `details`, что разворачиваются на экране итога.

Пёрышки за заход начисляет `syncCoins` (источник `drill`) — но только там, где
заход вообще сохранился, то есть по подписке: три штуки за заход, не
больше трёх заходов в день, и только если верных не меньше семидесяти процентов —
тот же порог, что у проверочной работы. Отбор строк вынесен в `pickPaidDrills` в
`lib/shop.ts`, чтобы его можно было проверить без базы. До этого тренажёры не
приносили пёрышек вовсе, и заход, который ничего не оставляет, читался ребёнком
как «это не считается».

## Кабинет взрослого

Кабинетов было два: `/roditel` со вкладками и `/repetitor` со списком учеников.
Половина экранов при этом существовала в двух адресах с одинаковым содержимым
(`/roditel/temy` и `/repetitor/temy`), а серверные ручки давно не различали, кто
задаёт: `requireAssigner` пускает обе роли. Разница на поверку оказалась
маленькой, и теперь она описана данными — `capsFor` в `lib/cabinet.ts`:

Роль **учётной записи** отвечает ровно на один вопрос: можно ли брать чужих
детей. Это не оформление, а обязательства — пригласить законного представителя,
дать ему подписать согласие, не знать его пароля. Отсюда же дверь с кодом: она
нужна только в семье, где вход в приложение один и компьютер общий с ребёнком,
и репетитору её предлагать незачем.

А «чей это ребёнок» — свойство **связи**, а не записи: оно лежит в
`child_access.role` и у одного взрослого бывает разным для разных детей. От него
зависит половина карточки:

- **личная заметка** и **код приглашения родителя** — только у ученика
  (`saveStudentNote` проверяет ту же роль в `child_access`);
- **лимит времени, звук, удаление профиля** — только у своего ребёнка: у
  ученика это решает его семья, а не педагог;
- слово «ребёнок» или «ученик».

Пока на этот вопрос отвечала роль записи, репетитор со своим первоклассником был
невозможен: всё, что он заводил, становилось учеником, которому он должен был
выслать приглашение самому себе. Теперь `addChild` заводит своего ребёнка любому
взрослому — и спрашивает у репетитора согласие законного представителя той же
строкой, что стоит в регистрации родителя (у родителя оно взято там).

Всё остальное — темы, тренажёры, домашка, отчёт — общее, и живёт по одному
адресу. Старые адреса не удалены, а переводят: из писем и закладок в них ещё
ходят.

Список `/kabinet` — один на обе роли, но разделами: у своего ребёнка в нём имя и
класс, у ученика — сдана ли домашка, что просело и принял ли родитель
приглашение. Учеников десяток, и заходить в каждого ради этого невозможно;
своих детей двое, и про них всё равно всё видно на их странице.

Порядок блоков на `/kabinet/$childId` — это и есть ответ на вопрос, что в
продукте главное. Сначала строка словами («занимался четыре раза, два дня
подряд»), потом пять тренажёров с рекордами, «открыть» и «задать» у каждого,
потом домашка, и только потом занятия по темам с историей и разбором. До этого тренажёры лежали
у родителя на третьем уровне — внутри вкладки «Задания», — а первым экраном
стояли четыре плитки про темы и минуты. История и доля верных по каждой теме
теперь под раскрытием: за ними приходят раз в месяц, а места они занимали больше,
чем всё остальное вместе.

Неделя и вывод словами считают заход в тренажёр наравне с занятием по теме. Пока
они смотрели на одни `lessons`, ребёнок, который всю неделю решал примеры на
время, получал в кабинете «не занимался на этой неделе» и семь пустых кружков.

Рядом с «задать» стоит «открыть» — и в разделе `/kabinet/trenazhery`, и на
карточке ребёнка: тренажёр можно пройти самому, прежде чем задавать. Такая
ссылка помечена `?proba=1`, и заход по ней не пишется никому. Без пометки он
уехал бы первому ученику в списке: ребёнка тренажёр берёт из `me()`, а о том,
что за экраном взрослый, знать ему неоткуда, — и в отчёте появились бы чужие
заходы, пёрышки и рекорды. Настройка в пробном заходе открыта по подписке
самого взрослого: ребёнок здесь ни при чём, а платит именно он (`drillWho` в
`lib/drill-search.ts`).

## Где проходит граница подписки

Главный продукт — тренажёры, поэтому запирать сами упражнения нельзя: по ним
приходят из поиска и из рекламы, и клик стоит единицы рублей. Заперто другое:

- **настройка захода** — разрядность и таймер в счёте, уровень в таблице, набор
  правил в правописании, скорость чтения, размер таблицы Шульте. Без подписки
  пилюли погашены (`fieldset[disabled]`), и настройки из адреса тоже не
  действуют: иначе замок снимался бы правкой строки в браузере. Гаснут при этом
  только невыбранные: базовая настройка остаётся синей, иначе открытый тренажёр
  выглядит как ряд одинаковых серых плашек, по которому не прочесть, с чем
  сейчас пойдёт заход;
- **сохранение результата** — `saveDrillRow` не пишет строку в `drills`, если у
  ребёнка нет оплаченного доступа (`childHasPaidAccess`). Вместе со строкой не
  появляются ни рекорд серии, ни динамика в кабинете, ни пёрышки: заход либо
  считается целиком, либо не считается вовсе, и объяснять ребёнку, почему одно
  посчиталось, а другое нет, не приходится;
- **темы** — как и раньше: бесплатно открыта первая тема каждого предмета.

Обе подсказки на экране тренажёра написаны ребёнку, а не взрослому: чаще всего
экран открывает он. Ссылки на оплату там нет по той же причине, по которой её
нет на замке темы: первоклассник не платит. Просьбы «покажи этот экран
взрослому» в них тоже нет — тот же адрес открывает педагог, зашедший
посмотреть тренажёр сам, и сказано коротко: подписка активируется в кабинете.

Доступ считается по ребёнку, а не по тому, кто смотрит: у ученика платит
репетитор, и родитель, зашедший тем же экраном, видит всё открытым, ничего не
оплачивая. Поэтому и выдача задания с настройками проверяется по каждому ребёнку
отдельно (`assignDrill`): в группе может быть и оплаченный ученик, и нет — задание
уйдёт обоим, но неоплаченному без настроек.

## Напоминания в мессенджер

Родитель привязывает канал сам: в кабинете во вкладке «Напоминания» он берёт код вида
`sov-7k2f9` и отправляет его боту. Бот приходит на вебхук
`/api/notify/tg` или `/api/notify/max` с общим секретом в query, приложение запоминает
chat_id и дальше шлёт короткое сообщение после каждой проверочной работы и тренажёра.
В сообщении только сам факт окончания занятия: ни имени ребёнка, ни темы, ни
результатов — этого требует п. 6.3 политики, обещающий, что персональные данные
оператору мессенджера не передаются. Логин мессенджера не спрашивается и не
хранится — только идентификатор чата.

Переменные окружения (в `.env` на сервере, пробрасываются в контейнер `app`):

| Переменная | Зачем |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен бота Telegram; без него канал не показывается в кабинете |
| `MAX_BOT_TOKEN` | токен бота MAX |
| `NOTIFY_WEBHOOK_SECRET` | общий секрет в адресе вебхука; без него ручка отвечает 404 |

Вебхук ставится один раз руками:

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://<домен>/api/notify/tg?secret=<СЕКРЕТ>"
```

Обработчик вебхука живёт в `src/lib/notify-webhook.server.ts` и вызывается из
воркер-энтри `src/server.ts` до роутера: это внешний POST, а не страница.

## Сообщения об ошибках

Кнопка «Сообщить об ошибке» стоит в углу каждого экрана: она смонтирована в
`routes/__root.tsx`, а не в подвале, потому что подвала нет на занятии, в нулевом
уроке, у ученика и в админке — то есть ровно там, где поломку и увидят.

Что происходит по «Отправить»: обращение сначала ложится в таблицу `bug_reports`,
и только потом уходит письмом на почту поддержки. Порядок именно такой — сказать
«спасибо, получили» и потерять текст, потому что почтовый сервис ответил
пятисоткой, нельзя. Ушло письмо или нет, видно в колонке `mailed_at` и в админке,
вкладка «Обращения».

К тексту сами прикладываются адрес страницы, браузер, время, id вошедшего и
выбранный профиль ребёнка. Почта для ответа необязательна; у вошедшего она
подставляется из аккаунта, и письмо приходит с `Reply-To` на неё.

От заброса форму держат три вещи: не больше пяти обращений в час с одного адреса,
предел в 2000 знаков и скрытое поле-ловушка. Адрес отправителя в базе не хранится —
только его SHA-256, потому что для счётчика этого хватает, а ночной дамп базы не
должен становиться журналом посещений.

| Переменная | Зачем |
| --- | --- |
| `SUPPORT_EMAIL` | куда слать обращения; не задана — адрес из `src/lib/support.ts` |

## Данные и приватность

- Аккаунт заводит взрослый. Согласия на обработку данных родителя и данных ребёнка
  собираются раздельно, факт и время фиксируются в таблице `users`.
- О ребёнке хранятся только имя, класс, аватар, ответы и время занятий.
  Почта, телефон и фотографии ребёнка не собираются.
- Пароли — PBKDF2-HMAC-SHA256, 100 000 итераций, случайная соль на пользователя.
- Сессии — HttpOnly-куки, срок 30 дней, сверка с таблицей `sessions` на каждом запросе.
- Профиль ребёнка доступен только своему родителю: проверка `requireOwnChild`
  стоит в каждой функции, принимающей `childId`.
- В обращении об ошибке хранится то, что человек написал сам, и почта, которую он
  оставил для ответа. IP не хранится — только его отпечаток для счётчика заявок.

## Индексация и превью ссылок

Список публичных страниц лежит в одном месте — `app/src/lib/seo.ts`. Из него берут
данные и `head` страницы (заголовок, описание, canonical, Open Graph, JSON-LD), и
`sitemap.xml`. Добавили публичную страницу — допишите её в `PUBLIC_PAGES`, и она
появится в карте сайта сама; забыть описание не даст TypeScript.

- Всё, чего в списке нет, объявляет `closedHead(title)` — заголовок и
  `noindex, follow`. Так закрыты кабинеты, вход, регистрация, оплата,
  приглашение и занятие конкретного ученика: без сессии робот увидел бы там
  форму входа.
- Закрытые адреса намеренно **не** запрещены в `robots.txt`: запрет обхода
  означает, что робот не прочитает и сам `noindex`, и адрес всё равно всплывёт
  в выдаче голой ссылкой. В `robots.txt` закрыто только то, что страницами не
  является: `/api/` и `/_serverFn/`.
- `canonical` и адреса в карте сайта — всегда с прод-домена `SITE_ORIGIN`, а не
  с хоста запроса. Тот же образ приложения отвечает и на превью-домене, и на
  localhost; разрешение на обход получает только прод. Робот, пришедший на любой
  другой хост, получает в `robots.txt` полный запрет. Своё имя приложение узнаёт
  из `X-Forwarded-Host` — его проставляет Caddy, из него же собирается адрес
  чека в кассе. **После первой выкладки проверьте один раз:**

  ```
  curl https://sovenok.space/robots.txt
  ```

  Должно быть `Allow: /`. `Disallow: /` означает, что до воркера не доехал
  заголовок с именем домена, и сайт закрыт от поиска целиком.
- `canonical` — без параметров запроса. Настройки тренажёров ездят в адресе
  (`/shulte?size=4`), и без этого каждая комбинация была бы для поисковика
  отдельной страницей с тем же текстом.
- JSON-LD получают только витрина (организация и сайт) и тренажёры
  (`LearningResource` с `isAccessibleForFree`). Документам разметка не
  достаётся: сказать про договор структурно нечего, а разметка, которая
  расходится с содержимым страницы, хуже отсутствующей.
- Оферта, политика и согласие отдают `noindex`, пока в исходнике документа
  остались поля `[[ЗАПОЛНИТЬ: …]]`: черновик, попавший в индекс, всплывал бы в
  выдаче ещё долго после того, как реквизиты допишут.
- Картинка превью (`og:image`) отдаётся абсолютным адресом: её забирает не
  браузер, а Telegram, VK или WhatsApp, и от относительного пути у части из них
  карточка остаётся без картинки.

Ни Google, ни Яндекс сайт сам не найдут — домен надо один раз подтвердить в
Search Console и Вебмастере и скормить им `https://sovenok.space/sitemap.xml`.
Подтверждение файлом кладётся в `app/public/`, подтверждение мета-тегом — в
`buildHead` в `app/src/routes/__root.tsx`.

## Какая база используется

Выбор базы задан явно, переменной `SOVENOK_DB`, а не выведен из наличия других
переменных. Раньше он был неявным — и потерянный `GATEWAY_TOKEN` не ронял
приложение, а тихо переводил его на пустую локальную SQLite: сайт открывался,
но без аккаунтов и прогресса, а новые регистрации уходили в базу без бэкапов.

| `SOVENOK_DB` | Что происходит |
| --- | --- |
| `postgres` | PostgreSQL через `db-gateway`. Без `DB_GATEWAY_URL` и `DB_GATEWAY_TOKEN` контейнер `app` не стартует — падает в `deploy/serve.mjs` до того, как займёт порт |
| `d1` (умолчания нет) | Биндинг `DB` — локальная SQLite в `/data/d1`. Путь отката, включается руками |

Умолчание строгое, `postgres`: прод без переменных обязан не подняться, а не
уехать на пустую SQLite. Задана переменная при этом всегда:
`docker-compose.yml` передаёт `postgres`, а `deploy/serve.mjs` подставляет то же
умолчание сам.

Ручка `GET /api/zdorovie` отвечает, к какой базе приложение подключено на самом
деле: `{"ok":true,"db":"postgres","engine":"postgres"}`. `db` — заказанный режим,
`engine` — движок, определённый запросом к самой базе; расходятся — 503. Данных,
версий и адресов ручка не отдаёт. Выкладка (`.github/workflows/deploy.yml`) ждёт
от неё именно `postgres`, иначе откатывается на прошлый тег.

## Первый запуск

Роль `admin` больше не достаётся первому зарегистрировавшемуся: служебные учётные записи
заводит `ensureServiceUsers()` в `deploy/db-gateway/server.mjs` из `ADMIN_EMAIL` /
`ADMIN_PASSWORD` и `TEST_EMAIL` / `TEST_PASSWORD`. Учебный контент создаётся автоматически
при первом обращении (функция `ensureSeeded`), повторно не дублируется.

Промокоды для активации подписки на пилоте: `SOVENOK`, `PILOT2026`, `SEMYA`.

## Оплата подписки

Карты принимает эквайринг T-Bank, кассовые чеки по 54-ФЗ выбивает подключённая к
тому же терминалу касса — это один личный кабинет и одна пара ключей. Тариф один
на обе платящие роли: 399 ₽ за месяц, 3 999 ₽ за год (`app/src/lib/billing.ts`
— цена в форме и цена в счёте берутся оттуда обе). Подписка разовая: автопродления
нет, карта не сохраняется, следующий период оплачивается заново.

Реквизиты карты в приложение не попадают. Кабинет создаёт счёт методом `Init` и
уводит человека на платёжную страницу банка, обратно приходит только адрес этой
страницы (сценарий без PCI DSS).

Суммы у банка в копейках, а в тарифах и в базе — в рублях, как их видит человек.
Пересчёт живёт только в `tbank.server.ts`: при выставлении счёта и при сверке
суммы из уведомления.

Доступ открывает уведомление банка, а не возвращение на сайт: адрес возврата
(`/oplata`) виден в браузере и набирается руками, поэтому страница возврата ничего
не решает, а спрашивает у базы, чем кончился счёт. Уведомление подписано так же,
как и запрос: значения корневых полей вместе с паролем терминала сортируются по
имени поля, склеиваются и хешируются SHA-256. Неподписанное получает 404.

| Переменная | Зачем |
| --- | --- |
| `TBANK_TERMINAL_KEY` | Terminal Key из личного кабинета эквайринга |
| `TBANK_TERMINAL_PASSWORD` | пароль терминала оттуда же; им же проверяется подпись уведомления |
| `TBANK_TAXATION` | система налогообложения в чеке, по умолчанию `usn_income` (УСН доход) |

Без ключей форма оплаты не показывается вовсе — в кабинете остаётся промокод.

Адрес уведомления руками в кабинете не ставится: он уезжает в самом `Init`
(`NotificationURL`) и всегда совпадает с доменом, с которого человек пришёл
платить — `https://<домен>/api/pay/notify`.

Обработчик живёт в `src/lib/billing-webhook.server.ts` и вызывается из воркер-энтри
`src/server.ts` до роутера — как и вебхук ботов. Отвечать он обязан ровно `OK` с
кодом 200: на любой другой ответ банк ставит уведомление в очередь повторов (раз в
час сутки, потом раз в сутки месяц) — этим и пользуемся, когда база недоступна.
При одностадийной оплате банк присылает два уведомления, `AUTHORIZED` и
`CONFIRMED`; доступ открывает только второе. Повторная доставка безопасна:
оплаченный счёт второй раз доступа не добавляет.

Сертификат `securepay.tinkoff.ru` выдан УЦ Минцифры, которого нет ни в одном
браузерном наборе корней, — без него вызов эквайринга падает внутри workerd, не
дойдя до кода приложения. Корень лежит в `deploy/russian-trusted-root-ca.pem` и
добавляется к обычным (не заменяет их) в `deploy/serve.mjs` и `deploy/stand.mjs`.
В `vite dev` SSR идёт обычным Node — там тот же файл подставляется переменной:

```bash
NODE_EXTRA_CA_CERTS=../deploy/russian-trusted-root-ca.pem bun run dev
```

Оферта публикуется по адресу `/oferta` из своего же исходника `docs/legal/oferta.md`
(второй копии текста в проекте нет). Пока в нём остались поля `[[ЗАПОЛНИТЬ: …]]`,
страница показывает заглушку вместо договора: черновик, выложенный по постоянному
адресу, — это уже оферта по пункту 2 статьи 437 ГК.

## Локальная разработка

```bash
cd app
bun install
bun run dev
```

Дев-сервер исполняет SSR в обычном Node, а не в workerd, поэтому базы там нет:
биндинг `DB` пустой, и страницы, которым нужны данные, скажут об этом из `db()`.
Витрина, нулевой урок и тренажёры данных не требуют и работают полностью.
Полное окружение с PostgreSQL — `docker compose up`.

### Стенд с базой без Docker

Когда нужны экраны с данными — ученик, репетитор, кабинет родителя, — а Docker
поднимать не хочется или негде, есть `deploy/stand.mjs`. Он собирает то же, что
и прод, из двух готовых частей: воркер в miniflare с биндингом `DB` поверх
локального SQLite (как `deploy/serve.mjs`) и asset-first раздача `dist/client`
(как `deploy/Caddyfile`). Один процесс, один порт, Caddy не нужен.

```bash
npm --prefix deploy install     # один раз, ставит miniflare
cd app && bunx vite build       # стенд запускает собранный бандл, не исходники
node deploy/stand.mjs           # http://localhost:8788
```

Стенд заводит в базе репетитора «Ирина Петровна» с четырьмя учениками и готовую
сессию — пароль при этом не задаётся, вход только по куке, которую скрипт
печатает при старте. Отключить фикстуру: `STAND_FIXTURE=0`.

База лежит в `deploy/.stand` (в гитигноре). Удалить папку — начать с чистой:
миграции идемпотентны и накатятся заново.

Важно: стенд работает **только** с локальным SQLite и сам пишет в базу учебные
строки. Если в окружении есть `SOVENOK_DB=postgres` или `DB_GATEWAY_URL`, он
откажется стартовать — чтобы фикстура никогда не уехала в боевую базу. И помните,
что прод живёт на PostgreSQL: SQL, который ведёт себя по-разному на двух движках
(строгий `GROUP BY`, приведения типов), стенд не проверит.

Две настройки в `vite.config.ts` живут только на время сборки и в dev
выключены — иначе дев-сервер не поднимается вовсе:

- `ssr.noExternal` — раньше стоял всегда, и SSR-раннер исполнял CJS-файлы вроде
  `react/index.js` как ESM, падая на `module is not defined` ещё до рендера;
- `ssr.external: ["cloudflare:workers"]` — в dev внешний модуль уходит мимо
  плагинов прямо в `import()` Node, где такого модуля нет. Там его подменяет
  дев-заглушка из `vite.config.ts`, отдающая `process.env` вместо биндингов.

## Бэкап базы

`deploy/backup-db.sh` снимает дамп PostgreSQL каждую ночь в 03:30 UTC (06:30 МСК)
из crontab пользователя `sovenok`. Скрипт лежит в репозитории и обновляется на
сервере выкладкой вместе с `docker-compose.yml` — править его на сервере руками
не нужно, правка потеряется.

Дампы складываются в `/home/sovenok/backups` в формате `-Fc`, хранятся последние
10 штук, старые удаляются. Сейчас один дамп весит около 130 КБ. Десять, а не
больше, — потому что политика обещает, что удалённые данные живут в резервных
копиях не более 10 дней; это число меняется только вместе с ней.

Восстановление целиком:

```bash
docker compose exec -T postgres pg_restore -U sovenok -d sovenok --clean < backups/sovenok-<дата>.dump
```

Дамп проверяется `pg_restore -l` до ротации: нечитаемый файл не сохраняется и не
вытесняет рабочие копии — иначе получился бы худший вид бэкапа, который есть, но
не восстанавливается. У cron некуда сообщать об ошибках, поэтому есть две точки
контроля: `backups/.last-success` с временем последнего удачного дампа и
`backups/backup.log` с историей.

Дампы содержат персональные данные детей и родителей, поэтому каталог `700`,
файлы `600`.

**Чего это ещё не даёт: копии лежат на том же диске того же сервера.** От
ошибочной миграции и случайного удаления они защищают, от потери сервера — нет.
Выгрузку во внешнее хранилище нужно доделать отдельно.

## Сертификат TLS

По умолчанию Caddy сам получает и продлевает сертификат Let's Encrypt — ничего
делать не нужно. Если требуется отдавать сертификат, выпущенный руками (например
НУЦ Минцифры), он подкладывается на сервере, а не в образ: ключ не должен попасть
ни в репозиторий, ни в слои публичного ghcr.

На сервере в `/home/sovenok/edtech`:

```bash
install -m 600 fullchain.pem certs/sovenok.pem && install -m 600 privkey.key certs/sovenok.key
install -m 644 russian_trusted_root_ca.cer certs/ca.pem
echo 'tls /certs/sovenok.pem /certs/sovenok.key' > caddy/tls.d/cert.conf
docker compose up -d web
```

`certs/ca.pem` — корневой сертификат выпустившего УЦ, и он обязателен. Проверка
живости в конце выкладки ходит на домен обычным `curl`, а тот сверяет цепочку
с системным CA-бандлом сервера, где корня НУЦ нет: запрос вернул бы `exit 60`
и код `000`, выкладка сочла бы живой прод мёртвым и откатилась на прошлый тег.
Увидев `certs/ca.pem`, она проверяет цепочку по нему. Файл содержит только
публичный корень — секрета в нём нет, в отличие от `certs/sovenok.key`.

`deploy/Caddyfile` подключает `caddy/tls.d/*.conf` глобом. Пустой каталог —
обычный Let's Encrypt; появившийся файл переводит домен на свой сертификат,
и за ACME Caddy больше не ходит. Откат — `rm caddy/tls.d/cert.conf` и тот же
`docker compose up -d web`, пересборка не нужна.

Глоб выбран намеренно: `import` одного файла роняет Caddy целиком
(`File to import not found`), если файла нет, — то есть уносил бы сайт при
первой же выкладке на чистый сервер. Пустой каталог Caddy переживает.

Важно про НУЦ Минцифры: его корневой сертификат по умолчанию есть только
в Яндекс.Браузере и Atom. В Chrome, Safari и Firefox страница откроется
с предупреждением о небезопасном соединении, если это единственный
сертификат домена. Отдавать оба сразу нельзя — браузер не сообщает, какому
корню он доверяет, поэтому выбирается что-то одно.

Сам сертификат заказывается на Госуслугах по ЭП юрлица или ИП, автоматической
выдачи у НУЦ нет. Продление тоже ручное — в отличие от Let's Encrypt, срок
нужно отслеживать самостоятельно.

## Перенос на собственный сервер

Приложение написано под Cloudflare Workers и D1. Для развёртывания на своей
инфраструктуре (например, при требованиях 152-ФЗ к размещению данных в России)
нужно заменить два места:

1. `src/lib/core.server.ts`, функция `db()` — вместо биндинга D1 подключить
   PostgreSQL или SQLite. Весь остальной код обращается к базе только через неё.
   Режим она берёт из `SOVENOK_DB`, см. раздел «Какая база используется».
2. Синтаксис запросов. Используется `prepare().bind().first()/.all()/.run()` и `batch()`
   в стиле D1; при переходе на PostgreSQL заменяются плейсхолдеры `?` на `$1, $2`
   и метод `batch` на транзакцию.

Схема в `migrations/0002_sovenok.sql` написана на стандартном SQL и переносится
почти без правок. Сборка под обычный Node вместо Workers меняется в `vite.config.ts`.

Регулярный дамп базы настроен, см. «Бэкап базы», но пока только на тот же диск:
от ошибочной миграции и случайного удаления он защищает, от потери сервера нет.
Выгрузку во внешнее хранилище нужно доделать.
