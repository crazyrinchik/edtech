# Совёнок

Платформа дополнительного образования для 1 и 2 класса: математика и русский язык
короткими занятиями. Три интерфейса в одном приложении — ребёнок, родитель, администратор.

Прод: https://sovenok.space

## Что умеет

**Без регистрации.** Нулевой урок из семи заданий (`/demo`), тренажёр устного счёта
(`/schet`) и тренировка скорочтения (`/chtenie`, простой уровень). Прогресс не
сохраняется, и на экране результата об этом сказано прямо.

**Ребёнок.** Карта тем с последовательным открытием, задания трёх типов (выбор варианта,
ввод ответа, сопоставление), мгновенная проверка, разбор ошибки словами вместо «неверно»,
проверочная работа с порогом 70% для зачёта темы, звёзды за пройденные темы,
мягкое напоминание об отдыхе через настраиваемый интервал. Любое задание читается вслух
по кнопке-ушку (синтез речи браузера) — читать для начала занятия не обязательно.
Если детей несколько, занятие начинается с выбора профиля по аватару и имени.

**Родитель.** Отдельный взрослый интерфейс без анимаций: доля верных ответов, минуты
и занятия за неделю, пройденные темы, зоны риска (темы с долей верных ниже 70%),
история занятий, результаты тренажёров, лимит времени и звук, управление подпиской,
несколько детей в аккаунте, напоминания в Telegram или MAX. Вход в приложение единый,
а кабинет открывается кодом из четырёх цифр.

**Администратор.** CRUD тем и заданий (существующие задания и темы правятся на месте),
DAU и WAU, конверсии (регистрация → первое занятие, доля открывших родительский кабинет,
доля оплативших), проблемные и популярные темы, блокировка пользователей и выдача
подписки вручную.

## Стек

- TanStack Start (React 19, SSR) + TanStack Router
- workerd (через miniflare) как рантайм — на своём сервере, не в Cloudflare
- PostgreSQL как база, доступ через внутренний шлюз с интерфейсом D1
- Caddy: статика, TLS, обратный прокси на SSR-worker
- Vite, TypeScript, Tailwind
- Zod для валидации входных данных серверных функций

Всё это крутится на одной машине в Яндекс.Облаке. В Cloudflare приложение
не выкладывается: персональные данные детей по ч. 5 ст. 18 152-ФЗ должны
храниться в базе на территории России. Конфигов для деплоя в Cloudflare
(`wrangler.jsonc`, `app.manifest.json`) в репозитории нет намеренно —
не возвращайте их. Юридическая обвязка живёт в `docs/legal/`.

## Напоминания в мессенджер

Родитель привязывает канал сам: в кабинете во вкладке «Напоминания» он берёт код вида
`sov-7k2f9` и отправляет его боту. Бот приходит на вебхук
`/api/notify/tg` или `/api/notify/max` с общим секретом в query, приложение запоминает
chat_id и дальше шлёт короткий отчёт после каждой проверочной работы и тренажёра.
Логин мессенджера не спрашивается и не хранится — только идентификатор чата.

Переменные окружения (в `.env` на сервере, пробрасываются в контейнер `app`):

| Переменная | Зачем |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен бота Telegram; без него канал не показывается в кабинете |
| `MAX_BOT_TOKEN` | токен бота MAX |
| `NOTIFY_WEBHOOK_SECRET` | общий секрет в адресе вебхука; без него ручка отвечает 404 |

Вебхук ставится один раз руками:

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://<домен>/api/notify/tg?secret=<СЕКРЕТ>"
```

Обработчик вебхука живёт в `src/lib/notify-webhook.server.ts` и вызывается из
воркер-энтри `src/server.ts` до роутера: это внешний POST, а не страница.

## Данные и приватность

- Аккаунт заводит взрослый. Согласия на обработку данных родителя и данных ребёнка
  собираются раздельно, факт и время фиксируются в таблице `users`.
- О ребёнке хранятся только имя, класс, аватар, ответы и время занятий.
  Почта, телефон и фотографии ребёнка не собираются.
- Пароли — PBKDF2-HMAC-SHA256, 100 000 итераций, случайная соль на пользователя.
- Сессии — HttpOnly-куки, срок 30 дней, сверка с таблицей `sessions` на каждом запросе.
- Профиль ребёнка доступен только своему родителю: проверка `requireOwnChild`
  стоит в каждой функции, принимающей `childId`.

## Какая база используется

Выбор базы задан явно, переменной `SOVENOK_DB`, а не выведен из наличия других
переменных. Раньше он был неявным — и потерянный `GATEWAY_TOKEN` не ронял
приложение, а тихо переводил его на пустую локальную SQLite: сайт открывался,
но без аккаунтов и прогресса, а новые регистрации уходили в базу без бэкапов.

| `SOVENOK_DB` | Что происходит |
| --- | --- |
| `postgres` | PostgreSQL через `db-gateway`. Без `DB_GATEWAY_URL` и `DB_GATEWAY_TOKEN` контейнер `app` не стартует — падает в `deploy/serve.mjs` до того, как займёт порт |
| `d1` (умолчания нет) | Биндинг `DB` — локальная SQLite в `/data/d1`. Путь отката, включается руками |

Умолчание строгое, `postgres`: прод без переменных обязан не подняться, а не
уехать на пустую SQLite. Задана переменная при этом всегда:
`docker-compose.yml` передаёт `postgres`, а `deploy/serve.mjs` подставляет то же
умолчание сам.

Ручка `GET /api/zdorovie` отвечает, к какой базе приложение подключено на самом
деле: `{"ok":true,"db":"postgres","engine":"postgres"}`. `db` — заказанный режим,
`engine` — движок, определённый запросом к самой базе; расходятся — 503. Данных,
версий и адресов ручка не отдаёт. Выкладка (`.github/workflows/deploy.yml`) ждёт
от неё именно `postgres`, иначе откатывается на прошлый тег.

## Первый запуск

Роль `admin` больше не достаётся первому зарегистрировавшемуся: служебные учётные записи
заводит `ensureServiceUsers()` в `deploy/db-gateway/server.mjs` из `ADMIN_EMAIL` /
`ADMIN_PASSWORD` и `TEST_EMAIL` / `TEST_PASSWORD`. Учебный контент создаётся автоматически
при первом обращении (функция `ensureSeeded`), повторно не дублируется.

Промокоды для активации подписки на пилоте: `SOVENOK`, `PILOT2026`, `SEMYA`.

## Локальная разработка

```bash
cd app
bun install
bun run dev
```

Дев-сервер исполняет SSR в обычном Node, а не в workerd, поэтому базы там нет:
биндинг `DB` пустой, и страницы, которым нужны данные, скажут об этом из `db()`.
Витрина, нулевой урок и тренажёры данных не требуют и работают полностью.
Полное окружение с PostgreSQL — `docker compose up`.

Две настройки в `vite.config.ts` живут только на время сборки и в dev
выключены — иначе дев-сервер не поднимается вовсе:

- `ssr.noExternal` — раньше стоял всегда, и SSR-раннер исполнял CJS-файлы вроде
  `react/index.js` как ESM, падая на `module is not defined` ещё до рендера;
- `ssr.external: ["cloudflare:workers"]` — в dev внешний модуль уходит мимо
  плагинов прямо в `import()` Node, где такого модуля нет. Там его подменяет
  дев-заглушка из `vite.config.ts`, отдающая `process.env` вместо биндингов.

## Перенос на собственный сервер

Приложение написано под Cloudflare Workers и D1. Для развёртывания на своей
инфраструктуре (например, при требованиях 152-ФЗ к размещению данных в России)
нужно заменить два места:

1. `src/lib/core.server.ts`, функция `db()` — вместо биндинга D1 подключить
   PostgreSQL или SQLite. Весь остальной код обращается к базе только через неё.
   Режим она берёт из `SOVENOK_DB`, см. раздел «Какая база используется».
2. Синтаксис запросов. Используется `prepare().bind().first()/.all()/.run()` и `batch()`
   в стиле D1; при переходе на PostgreSQL заменяются плейсхолдеры `?` на `$1, $2`
   и метод `batch` на транзакцию.

Схема в `migrations/0002_sovenok.sql` написана на стандартном SQL и переносится
почти без правок. Сборка под обычный Node вместо Workers меняется в `vite.config.ts`.

Настройте регулярный дамп базы во внешнее хранилище: репликация диска защищает
от отказа железа, но не от ошибочной миграции или случайного удаления.
